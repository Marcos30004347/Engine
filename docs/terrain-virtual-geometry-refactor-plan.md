# Terrain / Virtual Geometry Convergence Plan

Status: proposal

## Goal

Terrain streaming and virtual geometry should have the same runtime semantics.
The renderer should not need to know whether a page came from:

- an offline `.virtualgeometry` / future sparse-voxel asset;
- CPU-streamed prebuilt terrain or object data; or
- GPU-generated world terrain.

Those sources differ only in how page payload bytes are produced. Once payloads
exist in resident GPU buffers, hierarchy traversal, cut selection, culling,
lighting, Tree64 tracing, HZB rejection, and install/uninstall rules should be
shared.

The important rule is:

```text
CPU does not choose the runtime render cut.
GPU traversal chooses the cut from resident hierarchy state.
CPU only reserves storage, schedules/copies payloads, and applies safe rewrites.
```

This removes the semantic mismatch where a metadata publication transaction can
switch the runtime cut from the CPU side. A publication should make a page
resident and install its hierarchy rewrites; the next GPU traversal then decides
whether that page participates in the current LOD cut.

## Current mismatch

Virtual geometry already has the right shape:

1. Offline build creates hierarchy nodes, pages, dependencies, and install /
   uninstall rewrite lists.
2. Runtime streams page payloads into resident storage.
3. Page install rewrites update hierarchy visibility masks.
4. GPU traversal walks the current resident hierarchy and selects a view cut.
5. Parent-before-child dependencies and safe eviction avoid holes.

Generated terrain currently carries extra concepts around chunk publication and
renderer cut switching:

- terrain publication records can act like a separate ownership/cut authority;
- renderer-side code sometimes treats accepted terrain metadata as the visible
  cut;
- CPU-visible publication state can be ahead of, behind, or different from the
  hierarchy state used by raster and Tree64;
- page replacement can become a special terrain-only path instead of the same
  page install / uninstall rewrite system used by virtual geometry;
- a terrain chunk is not fully modeled as a normal streamed instance with an
  independent hierarchy and LOD cut.

That split is the kind of seam that produces holes: one system believes a child
is now authoritative while another system has not made the child payload,
parent fallback, or hierarchy masks visible in the same way.

## Target mental model

### Instance

A terrain chunk is a normal sparse-voxel instance.

Each instance owns:

- transform / world mapping;
- root hierarchy node range;
- page table range;
- resident page dependency state;
- independent LOD thresholds and error metrics;
- optional material-field bindings;
- optional Tree64 page bindings;
- debug identity.

Terrain is not globally special during traversal. A terrain chunk may have a
generator-backed page source, but once installed it is just another instance in
the scene.

### Page

A page is the unit of residency.

Every page has:

- logical page id;
- parent page id, or root/permanent status;
- dependency list;
- hierarchy node payload range;
- brick payload range;
- material payload range, when needed;
- optional Tree64 payload range;
- install rewrite list;
- uninstall rewrite list;
- generation/version number;
- resident physical allocation;
- state: missing, requested, producing, produced, copying, resident, retiring.

The page payload may be generated by GPU, decoded from disk by CPU, or copied
from a prebuilt cache. Traversal should not care.

### Hierarchy state

The hierarchy buffer is the only cut source.

Page install rewrites can:

- mark nodes resident;
- enable child masks;
- update child pointers;
- expose brick/material ranges;
- expose Tree64 page descriptors;
- update page generation words.

Page uninstall rewrites can:

- disable child masks;
- restore parent fallback;
- clear page table entries;
- retire physical ranges after fences.

The CPU may apply these rewrites, but it must not separately tell the renderer
"draw this terrain page now." The render cut emerges from GPU traversal of the
rewritten hierarchy.

### Tree64 sidecar LOD versions

Treat Tree64 data as a sidecar payload with its own streamable LOD versions,
not as a realtime mirror of every transient DAG cut.

For a terrain logical page, the producer may emit multiple immutable Tree64
versions:

- LOD0 / voxel-exact, used when the projected chunk error requires the finest
  lighting representation;
- LOD1, LOD2 and coarser conservative reductions, used when the current chunk
  error allows a cheaper lighting proxy;
- future prebuilt terrain/object sidecars using the same version table.

Each sidecar version is keyed by logical page id, geometry revision, Tree64
internal LOD, model payload revision, optional material sidecar revision, and
the maximum projected-error threshold it is allowed to represent.

During cut selection, GPU traversal still chooses geometry from resident
hierarchy state. The Tree64 view then asks for the coarsest resident sidecar
whose error threshold satisfies the selected page's projected error. If the
desired Tree64 version is missing, the frame must either use a resident ancestor
or coarser sidecar explicitly marked conservative, and emit a CPU streaming
request for the desired version. It must not silently trace empty space.

For generated terrain, the GPU can produce the requested Tree64 version into
scratch or final buffers. The CPU still owns the install transaction: reserve
physical Tree64 storage, validate generation/revision, install the descriptor,
and retire the previous sidecar after fences. This matches page installation
without forcing the GPU to rebuild a live Tree64 from the current runtime DAG
cut every frame.

A realtime DAG-cut-to-Tree64 update path remains a later experiment. It may be
useful if sidecar versions are too stale or too memory-heavy, but it is not the
baseline convergence contract.

## Required invariants

### Parent-before-child

A child page can only become visible if every ancestor required for fallback is
resident.

```text
install child page:
  require parent resident
  copy complete child payload
  apply child install rewrites
  child may now be selected by GPU traversal
```

### Eviction is child-before-parent

A parent page cannot be evicted while any installed child depends on it.

```text
evict parent page:
  reject if any child is resident / producing / copying / retiring
  apply parent uninstall rewrites only after descendants are gone
```

This is the same rule the user called out: we cannot evict a page unless all
children are also evicted, otherwise there is no guaranteed fallback and holes
are inevitable.

### Rewrite atomicity

The hierarchy must never reference a payload range that is not resident.

An install transaction becomes visible in this order:

1. CPU reserves physical ranges.
2. Payload producer writes into those ranges.
3. GPU/CPU copy or generation fence completes.
4. CPU applies install rewrites.
5. CPU publishes page table generation.
6. GPU traversal may select the page.

An uninstall transaction becomes invisible in the reverse order:

1. CPU applies uninstall rewrites so traversal falls back to parent.
2. CPU clears page table generation / resident bit.
3. Old physical ranges retire after all referencing GPU work completes.
4. Allocator reuses ranges.

### GPU cut selection

Every frame, GPU traversal starts from instance roots and decides:

- descend to resident children if projected error requires it and all required
  child pages are resident;
- otherwise emit the resident parent representation;
- never emit a node whose resident/payload generation is invalid;
- never skip both parent and child.

This is the terrain analogue of virtual geometry cluster cut selection.

### CPU responsibilities

CPU is allowed to:

- create instances;
- allocate logical page ids;
- reserve physical buffer ranges;
- schedule disk loads, CPU decompression, or GPU generation jobs;
- apply install / uninstall rewrites;
- update page table entries;
- collect delayed readback metadata;
- manage fences and retirement.

CPU is not allowed to:

- pick the view-dependent LOD cut;
- publish a special terrain visible set separate from hierarchy traversal;
- make a child visible before payload + rewrites are complete;
- evict a parent while a child can still be selected;
- rewrite hierarchy nodes to point at non-resident physical memory.

## Unified buffer model

Use the same sparse-voxel runtime buffers for generated terrain and ordinary
streamed instances.

Persistent GPU buffers:

- instance table;
- hierarchy nodes;
- child index / child mask table;
- brick nodes;
- brick occupancy;
- brick material records;
- material-field descriptors / pages;
- Tree64 nodes and page descriptors;
- page table;
- page dependency table;
- install/uninstall rewrite command buffers;
- per-page priority / feedback buffers.

The terrain GPU builder should not publish a separate terrain-only cut. It
should produce page payloads that can be installed into these buffers.

## GPU-generated terrain flow

The terrain generator becomes a page payload producer.

```text
GPU traversal / feedback
  -> page priority requests
  -> CPU allocator reserves destination ranges
  -> GPU terrain generator writes uncompressed page payloads into reserved scratch or final ranges
  -> optional GPU validation/compaction produces metadata readback
  -> CPU applies install rewrites
  -> next GPU traversal may select the page
```

The GPU should output uncompressed, renderer-native payloads:

- hierarchy node records;
- child index ranges;
- brick node records;
- occupancy words;
- material records / field references;
- Tree64 payload records, if generated with the terrain page.

If the generator needs variable-size output, use a two-stage reservation model:

1. GPU produces compact metadata: required node count, child count, brick count,
   material count, Tree64 count, checksum, page key, generation.
2. CPU reserves exact or size-class physical ranges.
3. GPU runs a copy/finalize job into those reserved ranges.
4. CPU installs rewrites after the copy fence.

For fixed-size terrain pages, CPU can reserve ranges before generation and the
GPU can write final payloads directly.

## CPU-streamed / prebuilt flow

Future prebuilt terrain and object data should use the same install path.

```text
GPU feedback requests page
  -> CPU loads compressed page from disk/network/cache
  -> CPU or GPU decompresses to renderer-native payload
  -> CPU reserves physical ranges
  -> copy payload into resident buffers
  -> apply install rewrites
  -> GPU traversal uses the same hierarchy state
```

No separate renderer code path is needed. The only source-specific difference
is the page producer:

| Source | Payload producer | Install path |
| --- | --- | --- |
| Generated terrain | GPU terrain generation jobs | shared page install rewrites |
| Prebuilt terrain | CPU/GPU decode from world package | shared page install rewrites |
| Static object | CPU/GPU decode from asset package | shared page install rewrites |
| Dynamic object | CPU-authored page upload or GPU build | shared page install rewrites |

## World-data map contract

The world generator already exports a versioned, co-registered map bundle. The
terrain runtime should treat those fields as streamed semantic inputs, not as
one-off CPU bake helpers.

Currently relevant exported data includes:

- elevation / height;
- uplift and relief / roughness;
- hydrology and river fields;
- climate fields such as temperature, precipitation and moisture;
- region, biome and landform classification;
- top-four biome ids and weights;
- source region id;
- placement-potential fields where producers already exist;
- manifest entries for future fields marked unavailable rather than silently
  encoded as zero.

The next terrain-facing schema additions should include explicit placement and
substrate fields:

- rock placement potential;
- rock type / geology class;
- cliff / exposed-bedrock mask;
- boulder / scree density;
- vegetation placement potential;
- vegetation type / ecotope class;
- canopy / ground-cover density;
- wetland / riparian vegetation mask;
- object exclusion / reserved gameplay mask;
- optional soil depth, substrate hardness and erosion-deposit fields.

These maps are not the final tree/rock instances. They are inputs for two
separate consumers:

1. the terrain page producer, which uses them to choose voxel material, surface
   detail, erosion/substrate response, and stable per-column metadata; and
2. a future placement/asset-streaming system, which reads the same world-data
   pages plus local terrain results and emits normal streamed instances for
   trees, rocks, grass clumps, structures and other meshes/voxels.

The generator should keep all fields co-registered: same world transform, same
texel centres, same gutters, same ancestor fallback, and explicit nearest vs
linear filtering rules. Categorical fields such as biome id, vegetation type,
rock type and exclusion masks must not be bilinearly interpolated as raw ids.
Continuous fields such as density, moisture, slope potential and roughness may
filter linearly.

## GPU chunk-generation instrumentation

Before the terrain generator depends heavily on these maps, add instrumentation
that proves each generated chunk can explain what inputs it used.

Per generated page/chunk, record:

- world-data pages sampled per field;
- lowest/highest sampled field LOD;
- missing-field fallback counts;
- ancestor fallback counts;
- categorical nearest-sample counts;
- continuous bilinear-sample counts;
- biome mixture summary;
- river/riparian sample summary;
- rock and vegetation potential min/mean/max when fields exist;
- generated brick count, occupied voxel count and material histogram;
- generated Tree64 node count, if emitted;
- payload byte counts by destination buffer;
- generation checksum and producer version.

Debug outputs should include:

- sampled biome id / biome weight;
- sampled river distance or river mask;
- sampled rock potential;
- sampled vegetation potential;
- chosen terrain material;
- page generation id;
- page source LOD;
- missing/fallback source marker.

This is deliberately diagnostic first. The first milestone is not better rocks
or trees; it is confidence that GPU-generated terrain samples the same world
semantics as `MapExportSampler` and the world-generator preview.

## Refactor stages

### Phase 0: freeze contracts and capture failures

Purpose: make the current behavior measurable before moving ownership around.

Tasks:

- Keep the current terrain renderer running.
- Add or keep captured world-data camera tests for close-ground LOD0 holes,
  shadow leaks and fast camera motion.
- Add counters for page install, page uninstall, parent fallback, child
  selection, invalid generation fallback and HZB rejection.
- Add a small synthetic streamed sparse-voxel hierarchy fixture that mirrors a
  terrain chunk but does not use the terrain generator.
- Add synthetic Tree64 sidecar fixtures for distinct LOD versions of the same
  logical page and verify error-driven selection/fallback.
- Document the current terrain-only publication/cut points that must disappear.

Exit criteria:

- A fixed camera can report whether a missing region came from cut selection,
  HZB/frustum, raster proxy coverage, Tree64 lighting, or page residency.
- Tests can fail on "selected neither parent nor child".
- Tests distinguish resident coarse Tree64 fallback from a missing desired
  Tree64 LOD request.
- Existing visual regressions are captured before the refactor begins.

### Phase 1: name the shared abstractions

Add terrain-neutral runtime types:

- `SparseVoxelStreamedInstance`
- `SparseVoxelPageId`
- `SparseVoxelPageState`
- `SparseVoxelPhysicalPageAllocation`
- `SparseVoxelPageInstallRewrite`
- `SparseVoxelPageUninstallRewrite`
- `SparseVoxelPageProducer`
- `SparseVoxelResidencyManager`

Terrain-specific names should move behind a producer implementation, not remain
in traversal/rendering.

Phase 1 implementation note: `SparseVoxelStreaming.hpp` now owns these neutral
names, and `docs/terrain-virtual-geometry-phase1-contract.md` records how CPU
assets, GPU terrain pages, future object pages and Tree64 sidecar ranges map
onto the shared contract.

Exit criteria:

- Terrain chunks, future object pages and CPU-loaded pages can all be described
  by the same instance/page/allocation/rewrite structs.
- No render pass needs a terrain-specific page state type to know whether a
  hierarchy node is resident.

### Phase 2: create the shared page table and allocator

Purpose: make residency state source-neutral before changing who produces the
bytes.

Tasks:

- Add a shared page table with logical page id, physical allocation,
  generation, resident bit, producer/source id, dependency counters and fence
  retirement state.
- Add shared physical allocators for hierarchy nodes, child indices, brick
  nodes, occupancy, materials, material fields and Tree64 sidecars.
- Add install/uninstall rewrite command storage that can target the shared
  hierarchy buffers.
- Keep root/coarse fallback pages pinned.
- Add debug readback for page state and physical ranges.

Phase 2 implementation note: `SparseVoxelSharedPageTable` and
`SparseVoxelPhysicalRangeAllocator` provide the first shared CPU-side residency
directory and fenced allocator scaffold. See
`docs/terrain-virtual-geometry-phase2-shared-page-table.md`.

Exit criteria:

- A CPU test can allocate pages, install children, reject unsafe parent
  eviction, uninstall children, and reuse physical ranges after a fence.
- No installed rewrite can point at an unallocated or retired physical range.

### Phase 3: split page production from page installation

Today, terrain generation, metadata publication, and visibility changes are too
close together.

Refactor into three explicit steps:

1. produce page payload;
2. reserve/copy payload into shared buffers;
3. apply hierarchy rewrites.

No render-visible state changes in step 1.

Phase 3 implementation note: `SparseVoxelProducedPagePayload` and
`SparseVoxelReservedPagePayload` stage producer output before installation, and
`terrainGPUV2ProducedPagePayload` converts V2 payload results into that neutral
metadata without publishing a terrain cut. See
`docs/terrain-virtual-geometry-phase3-production-split.md`.

Exit criteria:

- Terrain GPU V2 can produce payload metadata without changing the render cut.
- Install rewrites are the only operation that exposes a produced page to
  traversal.
- A stale late producer result is rejected by generation, not partially
  published.

### Phase 4: add a CPU/prebuilt page producer path

Purpose: prove the runtime is source-neutral with a simple producer before
moving all generated terrain.

Tasks:

- Build a tiny prebuilt sparse-voxel page package for tests.
- Decode/copy it into the shared physical buffers.
- Install it through the same rewrite path as terrain will use.
- Add an object instance that owns its own independent hierarchy and LOD cut.

Exit criteria:

- A CPU-loaded page and an equivalent generated/synthetic page produce identical
  traversal and raster output.
- Multiple instances can stream independently without sharing a global terrain
  cut.

Phase 4 implementation note: `SparseVoxelPrebuiltPagePackage` and
`sparseVoxelProducedPagePayloadFromPrebuilt` add the CPU/prebuilt producer seam.
Prebuilt packages may carry Tree64 fixture/LOD sidecar counts, but they still
install through `reserveProducedPagePayload`, `markPayloadCopied`, and
`installCopiedPagePayload`. See
`docs/terrain-virtual-geometry-phase4-prebuilt-producer.md`.

### Phase 5: make terrain chunks normal instances

For each terrain chunk:

- create an instance record;
- assign it a root page / root node;
- keep its coarse fallback resident;
- store its hierarchy and brick ranges in the shared buffers;
- let GPU traversal perform LOD cut selection exactly like other instances.

The terrain chunk should not be a special global cut inside renderer code.

Exit criteria:

- World terrain consists of many ordinary streamed instances or instance-like
  roots, each with independent page state and LOD.
- Coarse fallback is resident before any child page can be selected.
- Disabling terrain generation after roots are installed still renders fallback
  terrain, not holes.

Phase 5 implementation note: `terrainGPUV2StreamedChunkPages` and
`terrainGPUV2StreamedChunkInstance` map generated terrain chunks into normal
`SparseVoxelStreamedInstance` roots/pages, while
`selectSparseVoxelStreamedInstanceLOD` provides the shared fallback/desired-page
selection oracle. See
`docs/terrain-virtual-geometry-phase5-terrain-instances.md`.

### Phase 6: move terrain cut decisions fully to GPU traversal

Remove CPU-side concepts that publish a selected terrain cut.

GPU traversal should:

- read instance roots;
- test LOD error;
- check page resident/generation bits;
- descend or emit parent;
- write page priorities for missing desired children.

This is the virtual-geometry model: missing fine pages request streaming, but
the current frame still draws the best resident ancestor.

Exit criteria:

- CPU no longer publishes a terrain render cut.
- Runtime camera movement changes GPU traversal output and page priorities, not
  CPU-authored visible terrain sets.
- If a desired child is missing, traversal emits the resident parent and writes
  a streaming request.

Phase 6 implementation note: `traverseSparseVoxelStreamedInstancesLOD` is the
CPU oracle for the future GPU traversal pass. It emits the current resident cut
from instance roots/page-table state and produces view-derived missing-page
requests with no separate CPU terrain visible set. See
`docs/terrain-virtual-geometry-phase6-gpu-traversal-cut.md`.

### Phase 7: wire world-data map sampling into GPU terrain generation

Purpose: make GPU-generated chunks consume the same semantic data the world
generator exports.

Tasks:

- Bind `MapExportGpuPageCache` metadata, page table and physical page buffers to
  the terrain generation chain.
- Port or include the shared map-export sampling WGSL helpers in terrain
  generation shaders.
- Match `MapExportSampler` behavior for gutters, ancestor fallback, units,
  categorical nearest filtering and biome-mixture normalization.
- Sample current fields first: elevation, relief, hydrology/rivers, climate,
  biome/landform, source region and biome mixtures.
- Add unavailable-field handling so absent rock/vegetation maps produce explicit
  fallback diagnostics, not silent zero data.
- Emit per-chunk instrumentation listed above.

Exit criteria:

- GPU chunk generation and CPU `MapExportSampler` agree on sampled values for a
  set of fixed world positions and page-residency cuts.
- Missing semantic pages fall back to ancestors without invalid terrain
  materials.
- Generated terrain material histograms can be explained by sampled biome /
  river / climate inputs.

Phase 7 implementation note: `sampleTerrainGPUV2SemanticInputs` is the
CPU-visible oracle for the terrain column shader's map-export reads. It records
decoded values, requested/resolved pages, ancestor fallback, paired biome
normalization, required-page faults and explicit unavailable diagnostics for
source/rock/vegetation semantic probes without growing the fixed 20-slot V2
column config ABI. See
`docs/terrain-virtual-geometry-phase7-world-map-sampling.md`.

### Phase 8: extend world export for placement/substrate maps

Purpose: prepare terrain and later asset placement without mixing them.

Tasks:

- Add manifest schema entries for rock potential, rock type, exposed bedrock,
  vegetation potential, vegetation type, canopy/ground density, riparian mask,
  object exclusion and substrate/soil fields.
- Mark fields `available=false` until their producers exist.
- Implement producers incrementally, starting with low-risk continuous
  potentials derived from existing climate, slope, elevation, river distance
  and biome fields.
- Add preview/debug layers in `WorldGeneratorSample`.
- Add map-export read/write/hash tests for every new field.

Exit criteria:

- Terrain GPU generation can bind and sample new maps when available.
- Missing maps are visible in diagnostics and do not change output silently.
- The future placement system has a stable input contract but no renderer
  dependency.

Phase 8 implementation note: map export now declares the rock/vegetation
placement contract directly. Continuous maps derived from existing terrain,
river, climate, biome and substrate data are produced and paged
(`rock_potential`, `exposed_bedrock`, `vegetation_potential`,
`canopy_density`, `ground_density`, `riparian_mask`), while categorical
`rock_type` and `vegetation_type` remain `available=false` placeholders with no
payload until their producers exist. See
`docs/terrain-virtual-geometry-phase8-placement-substrate-maps.md`.

### Phase 9: unify eviction

Use one dependency-aware eviction policy:

- roots/permanent fallback pages are pinned;
- non-root pages are evictable only when no resident child depends on them;
- retiring physical ranges are fence-protected;
- uninstall rewrites happen before memory reuse.

This should replace terrain-only hidden/active group trimming semantics.

Exit criteria:

- Parent pages cannot be evicted while any child is resident, producing,
  copying or retiring.
- Eviction changes memory pressure and detail, not coverage correctness.
- Fast camera motion may lower detail temporarily but cannot produce black
  terrain holes.

Phase 9 implementation note: sparse shared-page eviction now goes through a
single `canEvictPage()`/`evictionDecision()` gate. Pinned roots/permanent
fallbacks reject eviction, and parent pages are protected while any dependent is
live or in-flight (`Requested`, `Reading`, `Decoded`, `UploadQueued`,
`Resident`, or `EvictPending`). Retired physical ranges, including Tree64
sidecar ranges, stay fence-protected until `reclaim()` completes. See
`docs/terrain-virtual-geometry-phase9-unified-eviction.md`.

### Phase 10: make Tree64 and lighting consume the same page generations

Purpose: prevent G-buffer and lighting from tracing different worlds.

Tasks:

- Treat Tree64 data as page sidecar payload or a dependency of the corresponding
  geometry page, with explicit LOD versions keyed by geometry revision and
  projected-error threshold.
- Store Tree64 descriptor generation beside geometry page generation.
- Make lighting trace reject/fallback using the same page table generation
  checks as G-buffer traversal.
- Request missing Tree64 LOD versions from CPU/GPU producers using traversal
  feedback, while tracing a resident conservative ancestor/coarser sidecar for
  the current frame.
- Add parity tests for screen traces enabled/disabled near LOD0 slopes and
  walls.

Exit criteria:

- A page cannot be visible in G-buffer without its required lighting sidecar, or
  lighting must explicitly fall back to the resident parent.
- LOD0, LOD1 and coarser Tree64 payloads for the same logical page can coexist
  in the stream/cache and are selected by projected error without changing the
  geometry cut.
- Screen-space traces and world traces agree near close terrain when both sample
  resident geometry.
- Shadow leaks through sub-voxel "windows" are tracked as missing sidecar /
  generation mismatches, not hidden in denoising.

Phase 10 implementation note: Tree64 sidecar requests now include an optional
stable logical page id and the scheduler keeps distinct internal LOD jobs for
the same logical page/geometry revision alive concurrently, while newer terrain
generations or geometry revisions supersede older jobs for that page. Lighting
selection has a CPU oracle,
`selectSparseVoxelTerrainTree64LightingSidecar`, which chooses matching
generation sidecars by projected error, requests missing desired versions, uses
only explicitly conservative same-page/parent fallbacks, and reports stale
sidecars as `tree64LightingMissCount` plus
`invalidGenerationFallbackCount`. See
`docs/terrain-virtual-geometry-phase10-tree64-generations.md`.

### Phase 11: future placement/asset streamer boundary

Purpose: consume rock/vegetation maps without turning terrain generation into
tree rendering.

Tasks:

- Define a placement candidate buffer keyed by world-data page, terrain page,
  seed and placement palette.
- Generate stable candidates from map fields plus local terrain outputs.
- Keep mesh/voxel asset loading in a separate streamed-instance system.
- Emit trees, rocks and vegetation as ordinary instances with their own page
  tables and independent cuts.
- Add exclusion/footprint feedback so placements do not punch holes in terrain
  or depend on terrain internals.

Exit criteria:

- Terrain pages can expose placement inputs, but they do not own tree/rock mesh
  streaming.
- Asset instances use the same sparse-voxel/virtual-geometry residency
  contracts.
- Disabling the placement system leaves terrain identical.

Status: done in
`docs/terrain-virtual-geometry-phase11-placement-boundary.md`.
`MapPlacement` now consumes the Phase 8 rock/vegetation density maps when
available. `SparseVoxelTerrainPlacement` adds the terrain/page keyed candidate
buffer, opaque footprint-exclusion feedback and a streamed-instance request

### Phase 12: remove terrain-only publication/cut code

Purpose: pay down the old semantic split once parity gates are green.

Tasks:

- Delete or narrow terrain-only visible-cut publication paths.
- Delete fragment/raster terrain ownership rejection that duplicates hierarchy
  cut logic.
- Replace terrain-specific active/hidden group trimming with shared page
  residency states.
- Keep only producer-specific scheduling, generation and diagnostics.

Exit criteria:

- The renderer has one sparse-voxel streamed hierarchy path.
- Terrain special cases are limited to data production, material semantics and
  debug UI.
- The old captured failures remain covered by tests.

Status: done in
`docs/terrain-virtual-geometry-phase12-shared-cut-authority.md`.
`TerrainGPUV2ResidencyManager` now exposes `sharedPageResidency()` so generated
terrain hidden/active chunks project into the shared `SparseVoxelPageId` /
`SparseVoxelPageState` contract. The old owner-group `publish()` path is
compatibility-only and rejects calls unless
`allowLegacyVisibleCutPublication=true`; Phase 7 explicitly opts into that
legacy coverage, while Phase 12 verifies generated terrain installs and
traverses through `SparseVoxelSharedPageTable` as the renderer-facing cut.

### Voxel LOD groups: brick clusters

The brick hierarchy needs the same grouping concept that virtual geometry uses
for cluster groups. A brick is the leaf cluster analogue: it is the exact
draw/trace payload. A voxel LOD group is a regular-grid macro-cluster over
nearby bricks at the same hierarchy level.

The group owns the perceptual LOD decision:

- group bounds are implicit from canonical grid origin and cubic side length;
- `sharedError` is conservative, initially the maximum `selfError` of all
  member bricks;
- `minimumError` / `maximumError` preserve the local error range for future
  quantized traversal queues;
- low `flags` bits mark occupied macro-cell faces that are
  silhouette-sensitive;
- `representativeNode` names the simplified top node when the group is formed
  from one parent and its children;
- every brick node has exactly one group index;
- groups are sidecar metadata and do not change page ownership or parent /
  child residency rules.

This is deliberately separate from publication ownership. Ownership groups keep
parent/child transactions atomic so holes cannot appear. Voxel LOD groups make
cut transitions spatially coherent so visible changes can happen inside a
chunk, not just on chunk boundaries.

Terrain is the ideal first producer because its source grid is regular. The
first implementation builds groups from each node's canonical grid origin and
scale using integer floor division, including negative page/chunk coordinates.
Later GPU phases can consume the same sidecar for culling, streaming feedback
and direct ray traversal without rebuilding a separate Tree64.

Crack prevention is a separate invariant from group-shared error. A group may
be cheap enough to draw coarsely and still be illegal if one of its occupied
boundary faces would meet a neighbour at a different silhouette resolution.
The GPU group cut must therefore treat boundary-flagged faces as edge-locked:

- if both sides of a boundary are resident, accept a mixed-resolution cut only
  when the coarse edge is a conservative match for the fine edge;
- otherwise refine both sides to a common boundary level, draw an explicit seam
  representation, or fall back to the resident parent that covers both sides;
- missing neighbour data cannot turn into empty space; it must request the
  desired page/group and trace or draw a conservative fallback for the frame.

For terrain this should be cheap: group boundary profiles come from regular
height/occupancy samples, so simplification can preserve border samples exactly
while simplifying the interior more aggressively. In practice that means a
coarse group can change the interior surface like a virtual-geometry cluster,
but its outer silhouette is constrained to match the neighbour's selected edge.

The preferred terrain grouping shape is parent-backed rather than a free bucket:
four child patches in XZ form the group and the parent node is the simplified
representative. Generic voxel volumes can use the equivalent 2x2x2 octree
group. Larger groups remain useful for experiments, but they need an explicit
simplification node before they can be accepted as crack-free render cuts.

### Phase 13: voxel LOD groups for brick-cluster cuts

Purpose: bring virtual-geometry-style cluster grouping to the voxel hierarchy
so terrain LOD changes are coherent patches inside chunks and can later drive
direct hierarchy tracing.

Tasks:

- Add a sidecar `SparseVoxelBrickLODGroupGPU` table plus node-to-group mapping
  generated by the brick hierarchy builder.
- Group bricks by hierarchy level and canonical regular-grid macro-cell, with
  configurable group side measured in bricks.
- Use conservative group error (`max(member.selfError)`) for the first cut
  metric, plus min/max member error for future local quantization.
- Mark occupied group boundary faces so later GPU cuts can reject or repair
  silhouette-incompatible mixed-resolution edges.
- Store the parent node as the group representative when a group maps exactly
  to one parent and its children.
- Keep the existing brick node ABI unchanged; upload/culling/tracing opt into
  the group sidecar in later phases.
- Add CPU regression tests for deterministic group membership, canonical
  bounds, negative-coordinate floor division, conservative shared error,
  boundary silhouettes and disabled-sidecar behavior.

Exit criteria:

- Brick hierarchy builds produce deterministic LOD group metadata.
- Every node belongs to exactly one group when grouping is enabled.
- Group bounds enclose every member brick in canonical grid space.
- Occupied group-boundary faces are recorded for later seam-safe cut selection.
- Existing terrain determinism tests remain green.

Status: Phase 13.0 done. The CPU data model and deterministic builder/tests
are in place. The first GPU consumer now lives in Phase 14; streaming feedback,
explicit seam repair and direct tracing remain follow-up work.

### Phase 14: group-driven GPU cut and streaming feedback

Purpose: consume voxel LOD groups during culling and streaming so screen cuts
and page requests become group-coherent.

Tasks:

- Upload the group sidecar beside brick nodes without changing legacy draw
  paths. Done for static/CPU-published hierarchies; full-GPU terrain pages
  still fall back until their producer emits the same sidecar.
- Add a feature flag for group-owned culling thresholds. Superseded by the
  safe data-driven gate: `lodGroupCount == 0` is the legacy path, valid
  representative groups opt into group-owned culling.
- Evaluate projected error once per group, then select member bricks from that
  group consistently. Done for parent-backed groups: the representative parent
  either wins for the whole group or all member children refine together.
- Before accepting a group at a coarser level, verify that every occupied
  boundary face matches its neighbour's selected silhouette level, or force a
  common boundary refinement/fallback.
- Emit streaming feedback for missing resident children/pages from the group
  decision, including geometry outside the current view when a trace demands it.
- Preserve parent fallback when a desired group is missing or still producing.

Tests:

- CPU/GPU cut parity on synthetic grouped hierarchies.
- Terrain camera-walk regression with chunk-edge LOD transition histograms.
- Synthetic adjacent-group mixed-LOD test where boundary mismatch must refine
  or fall back instead of showing a crack.
- Missing child group falls back to parent without holes.
- Out-of-view trace request emits page feedback without requiring screen
  visibility.

Status: Phase 14.0 partially done. The brick culling shader consumes
`SparseVoxelBrickLODGroupGPU`, `nodeLODGroupIndices` and
`representativeLODGroupIndices`, and CPU terrain commits publish those buffers
atomically with the accepted page-window cut. Boundary flags are present in the
contract but not yet neighbour-matched on GPU, so explicit seam repair remains
the next crack-hardening phase.

Purpose: test whether rays can traverse the installed brick/group hierarchy

Tasks:

## Migration details

### Keep parent pages resident

The initial terrain root/coarse pages should be permanent or very strongly
pinned. The system can still refine aggressively, but there must always be an
ancestor representation to draw.

### Use generation-checked descriptors

Every hierarchy node that references page-local payload should carry or derive
a generation check:

```text
node.pageId
node.payloadOffset
node.payloadGeneration
```

Traversal accepts the node only when:

```text
pageTable[node.pageId].resident &&
pageTable[node.pageId].generation == node.payloadGeneration
```

If the check fails, traversal must fall back to the parent path, not emit empty
space.

### Treat Tree64 as a sidecar page payload

Tree64 should be installed with the page it represents, or through a dependency
that cannot become visible before its corresponding geometry page is resident.

Lighting must not observe a newer/older cut than the G-buffer. The G-buffer and
Tree64 trace path should reference the same page generation table.

### Avoid terrain-only raster rejection

Raster/HZB culling can reject work, but only after the GPU cut has selected a
resident node. Fragment-side terrain-specific exclusion masks should not be
used as ownership/cut logic.

The raster path may use conservative proxies for performance, but DDA/hierarchy
state remains the exact visibility authority.

## Expected code movement

Likely current code to shrink or rename:

- terrain publication code becomes a `SparseVoxelPageProducer` implementation;
- `TerrainGPUV2Runtime` becomes a scheduler for producer jobs, not a cut owner;
- terrain page states become entries in the shared page table;
- terrain descriptor rewrites become ordinary install/uninstall rewrite lists;
- renderer terrain special cases become instance/source flags only where needed
  for generation, material fields, or debug display.

Likely shared code to grow:

- page allocator;
- rewrite application;
- dependency-aware eviction;
- resident generation validation;
- GPU traversal feedback/priorities;
- diagnostics for parent fallback vs missing child vs invalid generation.

## Acceptance criteria

The refactor is complete when:

- generated terrain chunks are represented as ordinary streamed sparse-voxel
  instances;
- CPU no longer publishes a terrain render cut;
- GPU traversal always selects the current cut from resident hierarchy state;
- parent fallback is guaranteed during generation, streaming, replacement, and
  eviction;
- generated terrain pages and CPU-loaded pages install through the same buffer
  and rewrite path;
- G-buffer, Tree64 lighting, and HZB culling observe the same page generation
  table;
- close-ground camera captures do not show missing chunks, triangular holes, or
  black terrain caused by residency transitions;
- disabling HZB/frustum culling changes performance, not correctness.

## Design preference

Make terrain boring.

The generator can be special. The data source can be special. The renderer path
should not be special. A terrain chunk should look like a normal streamed
instance with an independent hierarchy, independent LOD cut, resident parent
fallback, page dependencies, and install rewrites.

That symmetry is what lets future CPU-streamed prebuilt terrain, GPU-generated
terrain, and ordinary sparse-voxel assets share one correctness story.
